# CEO 領導與協作指南

本文件的讀者是「CEO」這個角色——也就是真正承擔商務判斷、簽核風險、提供外部資源的人類。目的不是教你怎麼改 agent 設定(那是 [`maintainer-guide.md`](./maintainer-guide.md) 的範圍),而是讓你知道在這套四部門十五員工編制裡,自己該做什麼、不該越權做什麼,才能讓 SOP 順暢運作,並拿到你要的結果。

## 一、你在這個架構裡實際要做的三件事

這套組織不是要你監督每一行程式碼,而是:

1. **校準商務真相**——只有你知道為什麼要做這件事、做給誰用、值得投入多少資源。PM 會主動追問,但你給的答案是所有下游決策的起點。
2. **簽核越權清單上「需要人類拍板」的事項**(見第三節)。
3. **提供 agent 自己拿不到的外部資源**——真人受測者管道、雲端預算、法律顧問、紅隊測試,這些 agent 設計上就不會自己生出來。

## 二、標準工作流程:任務該怎麼啟動

正確順序是 **PM 收斂 What/Why → RD 架構師出藍圖 → RD 工程師落地 → QE 驗證 → PM 把結果翻譯回你**。直接跳過 PM 把需求丟給工程師,會讓驗收標準變成事後才補,容易做出「對的程式碼、錯的功能」。

給 PM 的輸入,建議一次講清楚這幾件事(PM 也會主動追問,但你先講會省一輪來回):

- 這是要解決誰的什麼問題
- 驗收標準是什麼(要可驗證,不能是「用戶感覺順手」這種說法)
- 已知不做的範圍(二期、未來可能、暫緩項目)
- 交付形式(給投資人看的 deck、給客戶用的 MVP、還是內部 Notebook)

## 三、CEO 專屬決策清單

下表是整套 SOP 裡明確寫「需要 CEO 核准」的事項,完整版見 `cross-team.instructions.md` 第七節。沒有列在這裡的事,原則上各部門可以自行決定,不需要你逐項簽核。

| 事項 | 誰會卡在這裡等你 | 為什麼不能讓 agent 自己決定 |
|------|----------------|--------------------------|
| 移除 LICENSE 草案的「NOT FOR RELEASE」註記 | `tech-stack-curator` | 草案生效等於對外發布,法律責任在你 |
| 執行 `pip install` / `npm install` / `submodule add` | `tech-stack-curator` | 審查通過只是「建議採用」,實際安裝動作留給你手動執行 |
| 對正式環境的破壞性操作(刪資源、強制覆寫、降級資料庫) | `site-reliability-engineer` | 影響真實使用者與資料,需要 change window 或你的明確核准 |
| 提供真人測試管道(beta 名單、測試平台、招募預算) | `usability-test-coordinator` | 它無法自行招募、聯繫或支付真實受測者 |
| 啟動 skill / agent 考核 | `skill-quality-auditor` | 設計上不自動觸發,避免「自己改自己評」 |
| 確認考核優化結果是否採用 | `skill-quality-auditor` | 人在回路,每輪優化都要你確認才繼續 |
| `LICENSE` / `NOTICE` 重大條文變更 | 全公司 | 屬 PM 職權範圍,但條文變更仍需你核准 |
| push 到 `main` 分支 | 全公司 | 需要每次重新明確授權,不會因為前一次同意就自動延續 |

## 四、你必須知道的「做不到清單」

每個角色的 agent.md 都老實列出自己「做不到的事」,目的是讓你提早安排外部資源,而不是事後才發現缺口。

| 缺口 | 對應角色 | 你該怎麼補 |
|------|---------|-----------|
| 深度滲透測試 / 紅隊演練 | `security-engineer` | 找外部專業資安顧問或紅隊 |
| 法規合規認證(GDPR、HIPAA 等) | `security-engineer` / `site-reliability-engineer` / `testing-quality-engineer` | 找法律顧問,不要把 agent 的審查當成合規證明 |
| 大規模 / 跨雲災難復原演練 | `site-reliability-engineer` | 需要更高預算與專職 SRE 團隊,先評估是否現階段真的需要 |
| 真人質化可用性測試的招募 | `usability-test-coordinator` | 你提供 beta 名單、測試平台帳號或招募預算 |
| 大規模統計顯著的量化使用者研究 | `usability-test-coordinator` | 找專職 UX researcher 或市場調查公司 |
| 法規層級的無障礙合規認證 | `usability-test-coordinator` / `ui-ux-designer` | 找專職稽核,團隊只能做到符合 WCAG 設計基準 |
| 商務決策(要不要為某個 bug 延後上線) | 所有 QE / RD 角色 | 這條線永遠回到你或 PM,不應該由工程或測試角色自己拍板 |

## 五、給指令的實務建議

- 直接用 `@agent-name` 或從 Agent picker 選人,不需要每次重述這個角色的職責——`agent.md` 已經定義好,重述只會浪費你的時間。
- 看到下游回報「藍圖不可行」「依賴審查不過」「測試金字塔反了」時,不要逼著硬幹——這是設計內建的反向回報機制,代表上游該調整,不是哪個角色在偷懶。
- 引入新依賴前一定先過 `tech-stack-curator`,不要等 RD 或 QE 階段才發現授權或商用風險。
- 規模大到預期會被對話自動壓縮、需要跨 session 接續、或角色交接會「隔代」失真時,要求建立 `blueprint/<feature-name>/` 資料夾,讓每個角色把 Handoff Package 寫成檔案,而不是只在對話裡口頭交接。

## 六、部門間有分歧時,你什麼時候該出場

多數分歧不需要你直接下場仲裁:

- RD 和 QE 對 scope 該不該做吵架 → 回 PM 裁決,PM 是商務裁決的唯一窗口。
- 架構師和工程師對藍圖落地方式有分歧 → 工程師回報不可行,架構師調整藍圖,雙方在 RD 內部就能收斂。
- QE 發現資安疑慮升級給 `security-engineer`,或部署需求轉給 `site-reliability-engineer` → 這是平行分工的正常交棒,不是衝突。

真正該你出場的時機,是涉及**商務優先度取捨、預算、外部資源、法律風險、或正式環境核准**——這些事項本來就只列在你的決策清單裡(見第三節),其餘的若有人想跳過對應部門直接找你拍板,代表流程被繞過了,值得反問一句「這件事 PM / 架構師怎麼說」。

## 七、反饋循環:怎麼讓團隊真的越用越好

- 這次對話中你糾正了某個 agent 的假設或流程理解 → 明確說「優化 skill」「skill 評分」「達爾文」等觸發詞,讓 `skill-quality-auditor` 把落差記錄到 `feedback/session-log.md`。它不會自動啟動,需要你主動召喚。
- 這是產品 bug 或使用者問題,不是協作流程問題 → 留在產品 repo 的 issue 或文件裡,不要混進 HR 的治理型 feedback,兩者目的不同。
- 每次 skill 優化都是「人在回路」——達爾文跑完一輪評分與調整後會暫停,等你確認才繼續下一輪或回滾。

## 八、開新任務前的快速檢查清單

- [ ] 這個任務有沒有先經過 PM 定義 What/Why 與驗收標準,而不是直接跳工程實作。
- [ ] 涉及新依賴、框架或模型的,有沒有先過 `tech-stack-curator`。
- [ ] 規模大到可能跨 session 的,有沒有建立 `blueprint/<feature-name>/`。
- [ ] 涉及正式環境變更、真人受測者、或 LICENSE 對外發布的,有沒有還卡在等你核准的事項。
- [ ] 這次任務結束後,有沒有值得記錄到 `feedback/session-log.md` 的協作落差。
