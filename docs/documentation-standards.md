# 使用者文件標準

本文件說明 Connect AI 在 `.github` 內如何處理**面向使用者的人類文件**。這些文件包括 README、開發者文件、Pages 內容、維運手冊，以及產品中的使用者可見文字。

如果你的目標是讓 Copilot 遵守規則，請修改 `instructions/`、`agents/` 或 `skills/`。如果你的目標是讓人看得懂、照得做，請依本文件設計。

## 為什麼需要這份標準

目前的開發流程本來就包含技術文件、README、前後端文字與 Pages 文件。問題不在於文件是否存在，而在於這些內容若沿用 agent 常用的內部技術語氣，就會出現三個問題：

1. 讀者看到的是角色分工與治理語言，不是操作路徑。
2. 文件描述的是團隊怎麼思考，不是使用者怎麼完成任務。
3. 前端與文件文案開始像內部交接紀錄，而不是產品介面。

因此，流程上需要多一層**人類文件規則**，讓面向使用者的內容不再依賴作者個人習慣。

## 我們在 `.github` 內加入了什麼設計

為了解決這件事，`.github` 內增加兩個設計：

1. 一份會自動套用在使用者文件與 UI 文案上的 instruction：`user-facing-docs.instructions.md`
2. 一條固定的文件交付鏈：PM 定義讀者與成功條件，RD/QE 提供事實與證據，當前任務 owner 直接完成文件與文案；大型重構時由 `product-strategy-manager` 協調多方來源

這表示「面向使用者的文字表達」不再只是個人文筆問題，而是流程中的正式交付物。

## 什麼內容應該走這條流程

下列內容都應視為人類文件：

1. 根目錄 README
2. `docs/` 內的開發者與維運文件
3. GitHub Pages 上的技術與導覽頁面
4. HTML 頁面、按鈕、空狀態、提示文字、錯誤訊息
5. onboarding、quickstart、部署指南、使用手冊

## 這條流程怎麼運作

### Step 1：PM 定義讀者契約

PM 要先明確回答：

1. 這份內容是寫給誰。
2. 讀者完成哪個動作算成功。
3. 哪些承諾可以說，哪些不在範圍。

### Step 2：RD 與 QE 提供來源

1. RD 提供系統事實，例如架構、API、資料流、限制條件。
2. QE 提供驗證證據，例如成功路徑、測試結果、可追溯證據。

### Step 3：依文件規模決定是否升級

若只是一般頁面、單頁 README 段落或 UI 文案修改，當前任務 owner 直接依 `user-facing-docs.instructions.md` 撰寫即可。

若需要跨多頁重整讀者路徑、改寫 onboarding / quickstart 的整體資訊架構，或把多方來源收斂成單一對外文件，則由 `product-strategy-manager` 協調相關 owner 完成。

### Step 4：用固定文件型別出稿

每份內容應明確選擇以下其中一種型別：

1. 任務型文件
2. 概念型文件
3. 參考型文件

## 文件應該長什麼樣子

### 任務型文件

用於 README、quickstart、部署指南、操作手冊。

建議結構：

1. 這份文件會幫你完成什麼
2. 開始之前
3. 執行步驟
4. 驗證結果
5. 疑難排解
6. 下一步

### 概念型文件

用於角色邊界、架構概念、流程差異說明。

建議結構：

1. 這份文件說明什麼
2. 什麼時候需要理解這件事
3. 核心概念
4. 常見誤解
5. 下一步

### 參考型文件

用於欄位定義、設定表、契約與對照表。

建議結構：

1. 這份文件提供什麼參考
2. 欄位或值的定義
3. 範例
4. 限制與注意事項
5. 相關文件

## 哪些寫法要避免

下列寫法應避免出現在使用者文件與 UI 文案：

1. 內部角色分工語言，例如 PM、RD、QE 交棒紀錄
2. agent 規範語氣，例如「本 agent 應」「本輪修正」
3. PR 或 patch 歷程語氣
4. 沒有下一步的錯誤訊息
5. 只描述系統狀態，不描述使用者能做什麼

## 維護時如何判斷是否寫歪了

當你在修改一份人類文件時，快速檢查：

1. 讀者看到的是否是操作路徑，而不是團隊內部思考過程。
2. 標題是否能讓人一眼掃到自己要做的事。
3. 每個步驟是否只要求一個主要動作。
4. 文件是否明確告訴讀者成功長什麼樣子。
5. 若把 PM / RD / QE 字眼刪掉，內容是否仍然成立；若不成立，通常代表它還太內部。
