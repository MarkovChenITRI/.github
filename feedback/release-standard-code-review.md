# 發行版標準 Code Review 準則

本文件記錄 2026-06-25 專案清理過程中，CEO 對「有具體用途」的判準校正。後續 Connect AI 組織在本 repo 做 code review、文件審查、測試審查與架構清理時，一律以正式發行版與正式營運流程為預設標準。

## 背景

本次清理初期曾將「過去開發、debug、資料修補或歷史轉換時曾經有用」誤判為「目前仍有具體用途」。CEO 明確校正：

> 實際用途，是假設這個網站正式發布為前後端、資料庫及日常維運流程後所需的必要用途，而不是之前為了開發什麼東西或調整 debug 的實際用途。

因此，後續 review 不得以「曾經用過」、「可能某天用到」、「可作為備援」、「保留歷史比較安全」作為保留檔案、程式碼、測試、文件或流程的充分理由。

## 組織要求

所有部門與 agent 後續做 code review 時，必須先採用以下預設：

1. **發行版標準優先**：判斷內容是否應存在於 repo 時，以正式發布後的產品、資料庫、前後端功能、CI/CD 與日常維運是否需要為準。
2. **歷史用途不等於正式用途**：開發期 debug、一次性 migration、資料 backfill、盤點報告、臨時測試、舊版副本、demo placeholder 與「即將推出」互動，不因曾經有用就保留在主線。
3. **保留需要可驗證理由**：若主張保留，必須指出正式發行後的使用者、維運者、測試 gate、CI/CD、文件讀者或安全/合規需求會如何實際使用。
4. **不為假想需求保留入口**：沒有正式流程、沒有 owner、沒有驗收方式、沒有日常使用情境的內容，應移除或移出主線，而不是包裝成維運資產。
5. **測試也要符合發行版標準**：測試應保護正式行為與已承諾 contract，不應繼續保護已淘汰的一次性腳本、舊版 template、debug route 或 demo-only UI。

## Review 問句

審查任何檔案、函數、註解、文件、測試或 workflow 時，reviewer 必須先問：

- 正式發行後，誰會使用這個內容？使用入口在哪裡？
- 它支援的是產品功能、日常維運、CI/CD gate、文件讀者任務，還是只支援過去開發過程？
- 若移除它，正式使用者、維運者或 release gate 會失去什麼必要能力？
- 它是否只是 debug、backfill、migration、audit、old copy、placeholder、demo alert、歷史盤點或未落地規劃？
- 是否有測試或文件仍在保護已不屬於發行版主線的內容？

若上述問題無法給出正式發行版層級的答案，預設結論是移除或降級，不預設保留。

## 部門分工

| 部門 | Review 責任 |
| --- | --- |
| PM | 判斷功能、文件與流程是否仍屬 MVP / release 對外承諾。 |
| RD | 判斷程式碼、模組、函數與資料結構是否仍服務正式架構與 runtime。 |
| QE | 判斷測試、CI/CD、維運檢核與安全 gate 是否仍保護正式發行行為。 |
| Documentation | 判斷文件是否支援正式讀者任務，而不是保存開發過程。 |
| HR | 若此判準被 agent 重複違反，依 HR SOP 另行記錄 skill / SOP 落差。 |

## 本次校正案例

本次依此標準移除或降級的類型包含：

- `deployment/` 內一次性 SQL、migration script、runbook 與保護它們的測試。
- root-level 舊版 template 副本，因正式 route 已改用 `templates/pages/**`。
- 盤點過程文件與 backlog，因它們是開發協作過程，不是正式文件站必要內容。
- `docs/` 內不屬 MkDocs 任務頁的簡報二進位檔。
- category 頁面中沒有正式後端流程的 demo alert / 「即將推出」部署按鈕。

同時也確認某些看似可疑但仍有正式用途的內容應保留，例如：runtime schema bootstrap、admin bootstrap 訊息、安全測試中的惡意 URL payload，以及目前仍被 admin page 使用的 sidebar partial。

## 強制結論

後續本組織在本 repo 進行 code review 時，**一律以發行版為標準**。除非 CEO 明確要求保留歷史資料或研究紀錄，否則「過去 debug / 開發 / 調整資料時有用」不得視為具體用途。
