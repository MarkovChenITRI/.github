# 文件撰寫共通性原則回饋

## 日期

2026-07-14

## 分類

process-governance

## 前情提要

本次回饋來自 `docs/platform-maintenance` 文件 BEFORE / AFTER 規劃過程。使用者指出，前幾版修正過度聚焦於段落精簡、單頁局部修正與抽象審稿語言，沒有把文件撰寫的共通性原則明確保留下來。

此回饋適用於所有使用者文件、維運文件、README、docs、Pages 文件與使用者可見 UI 文案的撰寫規範。此回饋不是單一頁面修正建議，也不得只被 PM / RD / QE / HR 的團隊分工語言吸收成內部流程摘要。

## 必須記載到文件撰寫規範的原則

文件撰寫規範必須一字不漏、明確、具體地記載下列四項共通性原則，不可以被團隊分工而消化吸收：

1. 修改段落重點精簡，卻沒有考慮到敘述表達的起承轉合，還有上下文的敘述關係。
2. 要用台灣中文理解習慣的表達方式，並且避免抽象、概念、代表性的文字敘述。
3. 不要用反向論證語氣，請用正向事實描述語氣。
4. 交互參照只能在圖表前一段才第一次出現，不能在更早的段落出現。

上述四項是所有文件的共通性文字撰寫原則。後續更新 `.github/instructions/user-facing-docs.instructions.md`、文件撰寫 skill、文件審稿 checklist 或任何文件 owner SOP 時，必須明確保留這四項原文與其執行含義，不得只改寫成「降低認知負擔」「注意前後文」「使用正向語氣」「遵守圖表規則」等抽象摘要。

## 影響

若這四項原則只被吸收成團隊分工或抽象審稿語言，後續文件修正會再次出現下列風險：

1. 段落被縮短，但讀者仍看不懂前後邏輯。
2. AFTER 看似精簡，卻破壞原段落起承轉合或搶走後段內容。
3. 文件使用抽象、概念化或代表性詞彙，沒有符合台灣中文閱讀習慣。
4. 圖表交互參照提前出現，導致正文還沒有建立脈絡就要求讀者跳到圖表。
5. 團隊把使用者明確提出的文字要求消化成內部分工語言，造成下一輪審稿無法追溯原始要求。

## 實際決策

使用者要求將這四項共通性原則記載到 `.github/feedback`，並明確註明：必須一字不漏、明確、具體地記載到文件撰寫規範，不可以被團隊分工而消化吸收。

## 校正建議

後續更新文件撰寫規範時，應新增一節「文字撰寫共通性原則」或等價硬規則，逐字保留四項原則，並補上操作判準：

1. 修段落時必須同時檢查段落重點、起承轉合與上下文敘述關係。
2. 修文案時必須使用台灣中文可自然理解的具體說法，避免抽象、概念、代表性的文字敘述。
3. 修正說明時必須採正向事實描述語氣，避免反向論證語氣。
4. 圖表第一次交互參照必須只出現在圖表前一段，不能提前到更早段落。

這些規範必須保留為文字撰寫規則，不得改寫成 PM / RD / QE / HR 的交棒描述，也不得只寫成「由文件 owner 自行判斷」。
