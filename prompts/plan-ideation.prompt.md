# 計劃書敘述段落

依 `proposal-format.instructions.md` 的格式定義，段落層次與圖表位置參照 `.github/templates/ideation.md`，透過問答協助使用者建立或更新目標市場需求、產品開發與技術服務其中一段或兩段；這兩段彼此獨立，可以只處理其中一段。產出寫入 `<專案資料夾>/.github/proposals/<name>.md`。

## 開始之前

1. 確認要撰寫的計畫名稱；使用者未提供時，先詢問。
2. 確認這次要處理目標市場需求、產品開發與技術服務，還是兩段都要；使用者未指定時，先詢問。
3. 開啟 `<專案資料夾>/.github/proposals/<name>.md`，確認是否已存在：
   - 已存在且這次要處理的段落已有內容：告知使用者已存在，詢問要整組重新建立、還是局部更新；使用者選定後才繼續。
   - 不存在，或這次要處理的段落還沒內容：依下方問答建立。
4. 這次要處理產品開發與技術服務時，確認同一份 `<name>.md`「計畫架構與實施方法」段落是否已存在（`plan-action-items.prompt.md` 是否已經跑過）：
   - 已存在：沿用該段落定案的分項、子項名稱畫產品組成圖，不重新拆分。
   - 不存在：這次問答步驟順便問出分項、子項，供之後 `plan-action-items.prompt.md` 沿用。

## 問答步驟

依這次要處理的段落詢問，每段問完先覆誦使用者的回答，確認理解正確後再問下一段：

1. 目標市場需求：
   - 鎖定的使用者是誰，具體到有鑑別度（不是「使用者」，例如「電動巴士車隊的維修站」）。
   - 逐一詢問這個使用者目前面對的具體痛點：先問「現況怎麼運作」，再問「這個現況造成什麼具體後果」；問完一個痛點就問「還有其他痛點嗎」，重複到使用者明確表示沒有更多，且至少問到 3 個痛點為止。
   - 痛點之間有沒有因果或加乘關係，有的話問清楚關聯。
   - 這個需求有多急迫、多普遍：受影響的人數或案例數、發生頻率、既有做法的失敗率或事故紀錄，至少要有 1 項可查證的具體依據；沒有時如實記錄「使用者提供，尚待查證」。
2. 產品開發與技術服務：
   - 產品或服務整體是什麼、用哪些關鍵技術元件；逐一問每個元件解決上一步哪個痛點。
   - 依「開始之前」第 4 項的判斷：分項、子項已經沿用既有名稱時，跳過這步；還沒定案時，引導使用者從剛問到的關鍵技術元件拆出 2～3 個分項，每個分項再拆 2～3 個子項，依這組分項、子項畫產品組成圖（依 `proposal-format.instructions.md` 的規則）。
   - 逐一詢問每個關鍵技術元件對應的應用情境：誰在什麼狀況下操作、系統怎麼回應；問完一個情境就問「還有其他情境嗎」，重複到使用者明確表示沒有更多，且至少問到 3 個情境為止。每個情境依 `plan.instructions.md`「圖表類型的選用規則」問清楚內容性質，挑一種 Mermaid 圖表類型，問到能實際畫出這張圖。
   - 功能規格：技術指標（可直接量測，問數字與量測方式）與驗證指標（要場域驗證，問驗證方式與判定門檻）分開問，各自問到使用者明確表示沒有更多。

## 寫入計劃書（敘述段落）

1. 依 `.github/templates/ideation.md` 的段落層次與圖表位置、`proposal-format.instructions.md` 的內容規則，整理這次處理的段落內容。
2. 開啟 `<專案資料夾>/.github/proposals/<name>.md`，把這次處理的段落寫入或覆蓋既有段落；檔案不存在時先建立，其餘段落留待各自的 prompt 補上。
3. 在對話中貼出寫入的段落內容，請使用者確認。

## 完成條件

- **格式面**：`<專案資料夾>/.github/proposals/<name>.md` 已存在，這次處理的段落（目標市場需求、產品開發與技術服務其中一段或兩段）已存在——逐一對照 `proposal-format.instructions.md` 的段落欄位確認。
- **內容面**：這次處理的段落內容都有具體依據，讀者能根據這段做出判斷；判斷性詞（「市場很大」「需求很急迫」）已替換為陳述依據的講法。目標市場需求至少有 3 個具體痛點，每個都有現況與後果兩層說明；產品開發段落至少有 3 個應用情境，每個都配一張依內容性質挑選的圖表；技術指標與驗證指標都列出具體數字與量測或驗證方式。
- **程序面**：使用者已確認過寫入的內容。
