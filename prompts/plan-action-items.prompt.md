# 計劃書圖表段落

依 `proposal-schedule-format.instructions.md` 的格式定義，段落層次與圖表位置參照 `.github/templates/action-items.md`，透過問答協助使用者建立或更新計畫架構與實施方法、計畫時程、查核點三段；這三段有順序依賴，依序完成，不單獨拆開處理。產出寫入 `<專案資料夾>/.github/proposals/<name>.md`。

## 開始之前

1. 確認要撰寫的計畫名稱；使用者未提供時，先詢問。
2. 開啟 `<專案資料夾>/.github/proposals/<name>.md`，確認這三段是否已存在：
   - 已存在：告知使用者已存在，確認要整組重新規劃，還是只調整其中一段（調整單一段時，仍要依下方順序核對跟其他兩段的一致性，不能只改一段留下不一致的分項子項名稱或時間）；使用者選定後才繼續。
   - 不存在：繼續下方問答步驟。
3. 確認計畫名稱已定案且不需更動——時程與查核點確認後若名稱變更，成本很高；名稱未定時先行確認再繼續。
4. 開啟同一份 `<name>.md`，確認「產品開發與技術服務」段落是否已存在且已畫出產品組成圖（`plan-ideation.prompt.md` 是否已經跑過）：
   - 已存在：沿用該圖定案的分項、子項名稱，問答步驟直接依這組名稱展開，不重新拆分。
   - 不存在：這次問答步驟 1 建立分項、子項，供之後 `plan-ideation.prompt.md` 沿用。

## 問答步驟

依序詢問，每段問完先覆誦使用者的回答，確認理解正確後再問下一段：

1. 計畫架構與實施方法：
   - 依「開始之前」第 4 項的判斷：分項、子項已經沿用既有名稱時，直接跳到下一步；還沒定案時，使用者已有草擬版本時先請提供，依內容確認分項與子項，沒有草擬版本時，引導使用者從計畫目標拆出 2～3 個分項，每個分項再拆 2～3 個子項。
   - 逐一深入每個子項：具體的技術做法或研發方法是什麼、用到哪些技術元件或零組件（問到有具體名稱或規格數字，不是「相關技術」這種空泛講法）、依賴哪些其他子項、由誰負責、預期達成的具體量化結果是什麼；「做法」「技術或資源」「預期結果」三項都要問到具體才進下一個子項。
2. 計畫時程：依架構圖確認的分項子項，逐一詢問預計起訖時間與投入人月；分項的權重百分比要問到全部分項加總等於 100%。
3. 查核點：依分項分配英文字母代號，代號底下依完成時間先後編號；逐一詢問每個子項對應的查核點內容——要問到有具體量化指標，不能是「進度良好」這種沒有量測基準的講法；每個子項至少要有一個查核點，結案當月所屬的分項要確認有一個驗收用查核點。

## 寫入計劃書（圖表段落）

1. 依 `.github/templates/action-items.md` 的表格與圖表樣式、`proposal-schedule-format.instructions.md` 的內容規則，把架構圖畫成 `mindmap`、時程整理成逐月表格、查核點整理成里程碑代號表格。
2. 開啟 `<專案資料夾>/.github/proposals/<name>.md`，把這三段寫入或覆蓋既有段落；檔案不存在時先建立，其餘段落留待 `plan-ideation.prompt.md` 補上。
3. 在對話中貼出寫入的完整內容，請使用者確認。

## 完成條件

- **格式面**：`<專案資料夾>/.github/proposals/<name>.md` 已存在，計畫架構與實施方法（mindmap）、計畫時程（逐月表格）、查核點（里程碑代號表格）三段都已存在——逐一對照 `proposal-schedule-format.instructions.md` 的語法確認。
- **內容面**：架構圖、時程、查核點三段用的分項子項名稱與里程碑代號互相一致；每個子項的實施方法都涵蓋做法、技術或資源、預期結果三項具體內容；每個子項至少有一個查核點，查核點內容都是具體量化指標。
- **程序面**：使用者已確認過寫入的內容。
