# 系統架構撰寫 SOP

以顧問角色協助使用者收斂系統架構，分兩階段進行：第一階段從構想（或既有規格）拼出架構，第二階段比對業界作法後定案。

## 開始之前

1. 開啟 `<專案資料夾>/.github/specs/overview.md`，確認是否已存在：
   - 已存在：冷讀現有內容，依下列兩項建一份落差清單：
     - 依 `spec-format.instructions.md`「系統架構」段落的範本，把現有內容逐段對應到範本的欄位——這份範本是這次才定案，既有檔案通常是範本定案前寫的，對應不完整（例如目標使用者不明確、沒有明確的模組依賴關係、只寫了部分層級、用舊格式記錄）是預期中的常態；缺的部分記進落差清單，原本記載的資訊照樣保留，只補齊缺的部分。
     - 檢查內容本身有沒有自相矛盾（例如模組依賴關係圖畫出的模組，跟某層列出的模組清單對不上；跨層引用邊指向的模組，某一層根本沒列出；或某層描述服務對象、層間互動時提到的對象，在其他層找不到對應模組），矛盾的地方也記進落差清單。
   - 不存在：這是第一次使用 `plan`，先依 `spec-format.instructions.md` 的「目錄結構」，把兩種規格檔案結構（一層一檔／一模組一檔）攤給使用者選，選定後才繼續下面的步驟。overview.md 不存在代表這個專案還沒走過 `plan`；這個 repo 的標準流程固定是 plan 先於 implement、test，第一階段的起點只有使用者這次的口述構想。
2. `overview.md` 已存在時，再對照 `<專案資料夾>/src/` 底下實際的程式碼與 `<專案資料夾>/tests/` 底下實際的測試，確認目前的實作是否真的照規格書走，把新發現的落差併進步驟 1 的落差清單：
   - 落差清單是空的（規格書格式完整、內容前後一致、實作也跟規格書一致）：以規格書記載的內容為第一階段的起點，詢問這次是要更新哪一層、還是全部重新盤點。
   - 落差清單有內容：以規格書記載的內容為第一階段的起點，這份落差清單留到第二階段跟使用者逐項確認處理方式。

## 第一階段：從構想拼出架構

1. 請使用者描述這個系統的構想、規劃與理解——要做什麼、給誰用、大致怎麼運作。「給誰用」依 `spec-format.instructions.md` 的「目標使用者」骨架問到具體：是誰、要完成什麼、使用情境有什麼限制；答案太空泛時（例如只說「一般使用者」）追問到有鑑別度為止。
2. 拼湊出使用者介面層、應用層、領域層、基礎設施層各自應該有的模組，以及模組之間具體的引用需求——起點是「開始之前」冷讀到的既有規格內容（含跟實際程式碼比對後的結果，有的話），加上使用者這次口述的構想；依 `spec-format.instructions.md` 的「模組拆分粒度」判斷該拆或該合，依「依賴方向」只能由上層引用下層；描述不足以判斷的地方，直接問使用者，以使用者的回答為準。順便問清楚每一層服務的對象。
3. 依 `spec-format.instructions.md` 的「模組依賴關係圖」語法，把拼湊出的模組與引用關係畫成 Mermaid `graph`。
4. 依 `spec-format.instructions.md` 的「每一層的內容」規則，用文字段落交代每一層的模組與跨層互動關係，讓使用者能判斷是否符合他想要的東西。
5. 把圖與描述交給使用者確認是否符合預期：
   - 不一致：問清楚哪裡不一致，回到步驟 2 調整，重新畫圖、重新描述，再次確認。
   - 一致：進入第二階段。

## 第二階段：比對業界作法後定案

1. 從第一階段畫出的模組裡，篩出符合下列任一條件的模組或技術選擇作為研究範圍：
   - 換掉的成本很高（例如資料庫、訊息佇列、核心框架的選型）。
   - 要解決的問題不是這個專案獨有，業界大機率已經有成熟做法（例如身份驗證、金流、通知）。
2. 針對篩出的每個模組或技術選擇，上網搜尋：業界類似產品的作法、Arxiv 相關研究論文、開源程式碼專案。業界產品／論文／開源專案三種來源不用每種都有，但至少找到兩種來源、合計至少 2～3 個具體案例才算完成這一項的搜尋；找不到直接相關案例時，退而求其次找解決類似子問題的案例；仍然找不到時，如實記錄「這是這次專案的原創設計，沒有業界對照」。
3. 逐一比對搜尋到的內容，跟目前架構裡對應的模組或技術選擇有什麼異同。
4. 跟使用者逐項討論：哪些地方要做出差異化（為什麼要不一樣）、哪些要沿用既有技術以利用社群既有發展（用哪個 Benchmark 專案、為什麼可以直接沿用）；「開始之前」的落差清單有內容時，這裡也要逐項確認處理方式——格式或內容矛盾的落差，確認要怎麼改規格書；規格書跟實作不一致的落差，確認是要修改實作去符合規格書、還是規格書回頭更新去反映實作。
5. 依討論結果：
   - 架構圖或模組描述需要調整：回到第一階段對應步驟修改，改完再次跟使用者確認。
   - 不需要調整：把這一輪比對的結論（差異化理由、採用的 Benchmark 專案）記下來，供「寫入系統架構」使用。

## 寫入系統架構

1. 依 `spec-format.instructions.md`「系統架構」段落的範本，逐段填入：
   - 目標使用者：第一階段問到的是誰、要完成什麼、使用情境的限制。
   - 模組依賴關係圖：第一階段畫好的 Mermaid `graph`。
   - 使用者介面層、應用層、領域層、基礎設施層，各層寫成一段連貫文字，涵蓋這層的模組清單（第一階段拼湊）、技術堆疊與 Benchmark 專案（第二階段確認，附參考理由）、服務對象（第一階段問到）、跟其他層模組的互動關係（第一階段寫好的具體描述，模組名稱第一次出現時用粗體標示）。
2. 開啟 `<專案資料夾>/.github/specs/overview.md`，把整理好的內容依範本的段落順序寫入；檔案不存在時先建立。
3. 每一層列出的模組，附連結指到該模組實際的規格位置；模組還沒有規格時，連結位置附註「規格待建立」。
4. 在對話中貼出寫入的完整內容，請使用者確認。

## 完成條件

1. 寫入的內容段落順序與必填欄位，跟 `spec-format.instructions.md`「系統架構」段落的範本一致，段落齊全。
2. 每個模組與跨層引用關係都有具體到可判斷的描述。
3. 已完成第二階段的業界比對，比對後採用的 Benchmark 專案與參考理由已經寫進對應段落；研究範圍內每個模組都完成搜尋（找到案例或如實記錄沒有業界對照）。
4. 「開始之前」的落差清單有內容時，每一項都已經跟使用者確認處理方式。
5. 使用者已確認過寫入的內容。
