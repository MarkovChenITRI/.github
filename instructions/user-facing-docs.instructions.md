# 使用者文件與 UI 文案準則

本檔適用於所有**給人看**的內容：README、onboarding、quickstart、開發者文件、Pages 文件、維運說明，以及產品頁面上的使用者可見文字。目標不是讓內容看起來像 agent 規範，而是讓人能快速理解、照著做並完成任務。

## 一、先判斷這是不是人類文件

符合下列任一條件，就套用本準則：

1. 內容是給採用者、開發者、維運者、審查者或終端使用者閱讀。
2. 內容的成功標準是「人能完成任務」，不是「Copilot 能套用規則」。
3. 內容會出現在 Pages、README、docs、HTML 頁面、按鈕、提示文字、錯誤訊息或空狀態。

若內容是給 Copilot 執行的規則，請回 `.github/instructions/`、`.github/agents/`、`.github/skills/`，不要用本檔的寫法。

## 二、固定寫作模式

### 任務型文件

若文件是在教讀者完成一件事，優先使用這個結構：

1. 這份文件會幫你完成什麼
2. 開始之前
3. 執行步驟
4. 驗證結果
5. 疑難排解
6. 下一步

### 概念型文件

若文件是在解釋概念或邊界，優先使用這個結構：

1. 這份文件說明什麼
2. 什麼時候需要理解這件事
3. 核心概念或邊界
4. 常見誤解
5. 下一步

### 參考型文件

若文件是欄位、設定、契約或 API 對照表，優先使用這個結構：

1. 這份文件提供什麼參考
2. 欄位或值的定義
3. 範例
4. 限制或注意事項
5. 相關文件

## 二點五、審稿與定稿凍結 Gate

1. 使用者若是在問某段文案是否合格、是否回到標題、是否偏題、是否要檢討，先回答 `合格 / 不合格` 與理由；未獲明確改稿授權前，不得直接重寫。
2. 使用者一旦明示某段為定稿，或要求不要再動內容，該段立即視為 frozen；後續只能做評語、診斷、風險標註與替代方案，不得自行優化措辭。
3. 標題若是「這份文件會幫你完成什麼」或等價任務型標題，首句必須直接回答讀者能完成什麼；不得用內容摘要、章節總覽或範圍描述冒充任務說明。
4. 接近定稿階段時，預設工作模式改為 `review-first`；除非使用者重新明講要改，否則不得從審稿訊號自動切回 `rewrite-first`。
5. 使用者若貼出原文並要求「最小幅度修改」「局部改寫」或等價訊號，閱讀範圍可以涵蓋目標頁全篇與必要相鄰頁，但編修範圍預設只限被點名檔案與直接必要段落；不得因為讀了全篇就擴大成整頁重寫。
6. 這類窄授權回合要優先保留原段落結構、原資訊順序與原文案邏輯，只做滿足題目的最小差異修正；若判斷必須擴大改寫，先停下來說明斷層與理由，再等授權。

## 三、語氣與結構

1. 先寫讀者要完成什麼，再寫背景。
2. 標題要可掃描，直接描述讀者能做的事。
3. 步驟一律用編號清單。
4. 每一步只做一個主要動作；若讀者可能搞不清楚位置，先寫操作位置再寫動作。
5. 用命令式動詞起句，例如「執行」「選擇」「確認」「開啟」。
6. 若文件有成功條件，明確寫出讀者應看到什麼結果。

## 三點一、期刊式正文與圖表規則

1. 正文是主體，圖表是證據：正文必須先把概念、判斷、因果、邊界與理解路徑講清楚，圖表才出現。
2. 首次引用必須在圖表前：任何「如圖 1 所示」「如表 2 所示」「詳見表 3」等交互參照，都必須先在正文中出現，圖表才可往下放。
3. 圖表只放穩定事實：適合留在表格中的，通常是欄位名、分類、來源位置、驗證面向、條件類型、時間點、責任角色等穩定索引資訊。
4. 推論型內容不得藏進圖表：凡是「為什麼」「代表什麼問題」「若缺少會怎樣」「下一步怎麼做」「是否應拒發」這類推論、判讀與處置內容，都必須回正文。
5. 圖表前要先有導入段：導入段至少要回答三件事：這張圖表支援哪個論點、讀者看它要看什麼、它不能取代哪一段正文。
6. 圖表後不能才第一次解釋用途：caption 與圖表後補充只能做命名或閱讀提醒，不得在圖表出現後才第一次說明它是做什麼用的。
7. 表格不是流程，流程不是表格：若內容本質上是判斷順序、失敗路徑、處置建議、責任交接，優先寫成正文段落或編號步驟，不要為了整齊而做成表格。
8. 圖表的存在理由是壓縮，不是補洞：移除圖表後，正文仍應成立；若移除後正文會失去主要論證，代表該論點應回正文重寫。
9. Caption 只負責命名：caption 應簡短描述圖表名稱，不承擔正文尚未完成的論證責任。
10. 期刊式頁面優先 prose-first：若頁面屬概念說明、維運機制、設計規格或責任邊界頁，主體必須是段落論述，圖表只能作為輔助佐證。

## 三之三、Microsoft Learn Style 硬規則

1. 首屏優先：每頁前兩個段落必須讓讀者在不捲動太多的情況下看見目標、適用情境與第一個入口。
2. 短導言：導言以 2 段內完成；每段以 1 到 3 句為原則，不用長句塞滿 who、what、where、how、when。
3. 一頁一個主要任務：任務頁聚焦單一工作；概念說明與查表內容拆到獨立頁，不在同頁混成長篇總覽。
4. 標題要能掃描：標題優先寫讀者要做的事，例如「收集發布輸入」「確認查驗結果」「查看常見狀態」，避免空泛標題。
5. 先給入口再給細節：若步驟可能讓人迷路，先在步驟開頭寫 UI、頁面、系統位置或檔案位置，再寫動作。
6. Intro 不重複標題：標題已說明主題時，導言補的是任務、時機或成功結果，不重複改寫同一句標題。
7. 程序與參考分開：操作流程用編號步驟；名詞對照、狀態表、欄位表用表格；不要把表格當流程，也不要把流程寫成敘事段落。
8. 段落短且可掃描：多用短句、短段、短清單；長段落拆成小節，不讓讀者在單一段落中同時處理多個判斷。
9. 固定模式一致：相似頁面使用相似順序，例如「開始之前」「執行步驟」「驗證結果」「常見問題」「下一步」；不要每頁都換結構。
10. 直接幫讀者完成任務：用簡單、直接、可執行的語氣；少講治理心法，多講讀者現在在哪裡按、看什麼、判斷什麼。
11. 連結要有目的：交叉連結只在讀者真的要切頁時出現，並說明切頁目的，例如查契約、排障或看參考表。
12. 驗證要可觀察：任務頁至少有一節明確寫出成功訊號，讓讀者知道做完後應看到什麼狀態、輸出或下一步入口。

## 三之一、4W1H 寫作硬規則

1. 每頁開頭第一段必須明寫 `who`、`when`、`what`，句型優先使用「當你是誰、在什麼情況下、要完成什麼，就看這一頁」。
2. 每個步驟都必須先寫 `where`，再寫 `how` 與 `what`；句型優先使用「在某頁面或某系統位置，執行某動作，確認某結果」。
3. 每個名詞第一次出現時，必須在同頁交代它在哪裡看得到，不能只丟名詞後把讀者送去別頁查。
4. 任何表格欄位若寫「輸入」「資料」「證據」「結果」，都必須補一欄「取得位置」或「觀察位置」。
5. 任何表格欄位若寫「狀態」「判定」「完成條件」，都必須補一欄「誰更新」與「何時更新」。
6. 不可只寫籠統角色名，例如「平台維護者」；要明寫建立草稿者、核發授權者、接收發布結果者、技術查驗者、發布決策者等具體角色。
7. 不可只寫抽象動作，例如「確認」「核對」「補齊」「回查」；要補上實際操作位置、欄位名稱或比對對象。
8. 主流程頁只能描述正常路徑；異常處理集中放在例外分支頁，避免主流程與排錯流程混寫。
9. 每頁最後都必須提供可觀察成功訊號，句型優先使用「完成這頁後，你應看到什麼狀態、留下什麼紀錄、進入下一頁哪個步驟」。
10. 每一頁至少要出現一次完整 4W1H 句型，讓第一次接手的人不跳頁也知道第一步怎麼開始。

## 三之四、圖表欄位合法性檢查

1. 若表格欄位名稱含有「為什麼」「原因」「風險」「影響」「後果」「建議」「下一步」「代表什麼問題」，預設視為非法欄位，應改寫回正文。
2. 若表格每一列需要靠句子推理才成立，而不是直接查值或對照，預設不應維持表格型態。
3. 若圖表出現後，正文才第一次解釋圖表支援哪個論點，視為閱讀順序錯誤，必須前移解釋段落。
4. 若圖表承擔主流程、主判斷或主要讀者路徑，視為 prose-first 失敗，應改由正文重建主體。
5. 參考型頁面可以保留高密度表格，但任務型與概念型頁面中的圖表只能輔助，不得壓過正文主體。

## 三之二、禁句型

1. 不得用負向對比句推進說明，例如「不是 X，而是 Y」「不要 X，直接 Y」「不是主流程，而是例外分支」。請改成正向描述，直接寫這一頁是什麼、讀者現在要做什麼。
2. 不得用排除式句型定義讀者任務，例如「你現在要查的不是 A」。請改成正向句型，直接寫「你現在要查的是 B」。
3. 不得用禁止句當主要指引，例如「不要跳頁」「不要手動補欄位」。請改成操作指引，直接寫下一步該去哪裡、該改哪個來源。
4. 不得靠抽象否定建立權威，例如「不能宣布完成」「不應存在口頭訊息」。請補上具體完成條件、寫回位置與可觀察結果。

## 四、禁止把內部語言直接給使用者

下列語言不得直接丟給使用者，除非文件本身就是在解釋內部治理流程：

1. 「agent 應該」「skill 落差」「session insight」「上下文汙染」
2. 「PM / RD / QE / HR 交棒」這類內部分工語言
3. 「這輪修了什麼」「本次 patch」「PR 歷程」這類開發紀錄語言

需要保留的，應轉成讀者可理解的操作語，例如：

- 內部語言：`verification evidence package`
- 對外語言：`驗證結果與可追溯證據`

## 五、使用者可見文案規則

套用到 HTML、JS 或 UI 文案時：

1. 優先寫行動與結果，不寫內部系統狀態。
2. 錯誤訊息要告訴使用者下一步能做什麼。
3. 空狀態要說明目前沒有什麼、可以做什麼。
4. 不把內部欄位名、資料表名、角色名直接暴露成主要文案。
5. 不用「理論上」「應該」「正常來說」這類不負責任語氣。

## 六、正式交付前的來源檢查

任何使用者文件或 UI 文案，在定稿前都要能對應到三類來源：

1. PM 的 reader / product context package
2. RD 的 system facts package
3. QE 的 verification evidence package

若缺其中任一來源，不得把內容包裝成既成事實。

## 七、交付責任

1. `product-strategy-manager` 定義讀者、成功條件與交付形式。
2. 當前任務 owner 可以直接依本準則撰寫使用者文件與 UI 文案。
3. RD 提供系統事實，QE 提供驗證證據。
4. 若任務涉及跨頁重構、資訊架構調整或多方來源收斂，則由 `product-strategy-manager` 協調 reader contract，並由相關 owner 共同完成。
5. 任何角色都不應直接以內部工作語氣定稿使用者文件。

## 八、跨頁重寫與整組一致性

1. 只要同時改動多頁、重設頁名、改變讀者路徑、重整資訊架構、重命名共用名詞，這次任務就屬 section-level work，不得當成單頁 patch。
2. 跨頁文件重寫在動筆前，必須先凍結 `Page Inventory 與寫作契約`、`Reader Matrix`、`Actor / Responsibility Matrix`、`Canonical Terminology Table`、`Source-of-Truth Map` 與 `Deferred Claims List`；缺任一項時，只能產出 `draft-placeholder`、`deferred` 或等價草稿。
3. 改一個核心名詞、頁名、流程段名或角色名時，必須同步檢查整個受影響 scope 的標題、導言、表格、交叉連結、相鄰頁與 pointer / reference 頁；不得只改眼前一頁。
4. 同一頁只能有一個主要讀者；若需要提到其他角色，應寫成交接、分流或參考入口，不可在頁內中途換讀者立場。
5. 每個條件分支、例外情況與退回處理，都必須明寫下一步由誰處理，不能只寫「請確認」「請補件」而不交代 owner。
6. 修正任何頁面前，必須先完整閱讀目標頁全篇與牽動同一讀者路徑的相關頁面；關鍵字掃描只能用於修正後確認殘留用詞，不能取代完整閱讀。
7. 使用者若只授權局部改寫，完整閱讀的目的只能用來維持上下文一致與避免斷層，不能把它當成擴大修改範圍的理由。

## 九、詞彙治理

1. 同一個資料物件、流程段、狀態、角色或交付物，在同一個 scope 內只能使用一套主名稱；若要改名，先改 `Canonical Terminology Table`，再展開全文修訂。
2. 描述責任、資料內容、驗收條件與維護行為時，優先用台灣中文具體操作語；避免只寫「流程」「內容」「資料」「結果」「設定」「問題」「支援」這類未交代 handled object 的空泛名詞。
3. 內部英文名詞、API 路徑、資料表欄位與 enum 可保留原文，但在任務型與概念型頁面第一次出現時，必須同頁補上白話名稱與觀察位置。
4. 正式文件若必須保留內部名詞，應限於參考型或契約型頁面；操作型頁面不得把內部名詞當主要教學語言。
5. 術語修訂完成前，不得宣稱該 doc set 已定稿；必須完成整個 scope 的標題、導言、表格、交叉連結與相鄰頁掃描。

## 十、整組定稿前驗收

1. 來源完整性：PM 的 reader / product context package、RD 的 system facts package、QE 的 verification evidence package 三者都存在，且對得上這次交付範圍。
2. Reader-path audit：從入口頁走到相鄰主流程頁、補充頁與 reference 頁，確認同一路徑不會中途換立場、換名詞或換成功條件。
3. Actor trace：逐段確認每一步、每個條件分支、每個退回情境都能指出下一位行動者。
4. Terminology sweep：確認同一個資料物件、狀態、流程段與角色，在整個 scope 內名稱一致。
5. Cross-link audience audit：確認每條交叉連結都指向正確讀者的下一步；若目標頁面是不同讀者，必須明寫切頁目的。
6. Cold-read review：未參與對話的人，只看首屏與主要步驟，就能判斷這頁是給誰看、在處理什麼、完成後要去哪裡。
7. Build、link check、grep、lint 與無語法錯誤只屬必要條件，不足以單獨證明文件已完成。

## 十一、快速檢查清單

- [ ] 標題可掃描，能直接描述讀者要完成什麼。
- [ ] 若標題是「這份文件會幫你完成什麼」，首句真的直接回答讀者能完成什麼，不是內容摘要。
- [ ] 文件結構符合任務型、概念型或參考型其中一種。
- [ ] 讀者能看出開始條件、操作步驟、成功結果與下一步。
- [ ] 每頁都能回答 who、what、where、how、when。
- [ ] 這一輪若屬 review / 檢討 / 問責，已先回答判定與理由，沒有未授權改稿。
- [ ] 使用者已標示定稿的段落沒有被自行重寫。
- [ ] 若為跨頁重寫，已先凍結 reader、actor、術語、來源與 page inventory 契約。
- [ ] 每個條件分支、例外處理與退回情境都寫明下一步 owner。
- [ ] 沒有只局部替換名詞、頁名或角色名；整個受影響 scope 都已同步掃描。
- [ ] 已完成 terminology sweep、reader-path audit、cross-link audience audit 與 cold-read review。
- [ ] 每張圖表第一次被引用的位置都在圖表本體之前。
