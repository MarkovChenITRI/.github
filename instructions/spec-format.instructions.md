# 規格書格式

規格書分三部分：系統架構交代整個專案的技術總覽，模組規格交代單一模組的細節，使用範例／驗收標準交代單一使用者操作流程的驗收條件。前兩部分寫進 `.github/specs/**`，格式定義在這份檔案裡；使用範例／驗收標準寫進 `tests/operations/**`，格式定義在 `operations-test.instructions.md`，不在這裡重複。

## 系統架構

整個專案固定一份 `.github/specs/overview.md`，記錄這個專案的系統架構。系統架構採用 DDD 分層設計，固定四層：使用者介面層、應用層、領域層、基礎設施層。

### 這個專案的系統架構內容

依四層各自條列：

- What：這層目前有哪些模組，附連結指到各模組的規格位置。
- Where：這層主要使用的技術堆疊，以及這層設計時參考或依附的 Benchmark 開源專案庫。
- How：這層跟其他層怎麼互動；也交代這層的模組、Benchmark 開源專案庫、技術堆疊三者怎麼形成閉環邏輯——技術堆疊支撐模組運作、模組設計參考 Benchmark 專案、Benchmark 專案驗證技術堆疊的選擇是否合理，依實際情況描述這個循環怎麼成立。附一張 Mermaid 圖示範這個閉環。
- Who：這層服務的對象。

搭配一張 Mermaid 圖固定四層的相對位置與互動關係。第一次建立、或任一層新增／刪除模組時，由 `plan` 負責回來更新。

## 目錄結構

每個專案第一次使用 `plan` 時，先跟使用者盤點這個專案預期會有哪些模組，再從下列兩種目錄結構讓使用者選一種：

- 一層一檔：`.github/specs/<layer>.md`，同一層的所有模組共用一份檔案，各佔一段。
- 一模組一檔：`.github/specs/<layer>/<module>.md`，每個模組獨立一份檔案。

## 模組規格欄位

不管哪一種目錄結構，每個模組固定四個欄位：

```markdown
## <模組或功能名稱>

- Who：負責維護與變更核准者
- What：這個模組負責什麼；明確排除項
- How：（見下方「How 欄位的骨架」）
- Where：檔案路徑、命名慣例
```

### How 欄位的骨架

How 欄位不是一句話，依下列骨架展開：

1. **開場定位**：這個模組的 How 要幫誰查什麼——誰會在什麼情境下需要查這一段，查完應該能判斷什麼。
2. **依賴關係與對外介面**：這個模組依賴誰、被誰依賴、對外提供什麼方法或介面。
3. **選一張圖，圖後接讀圖指引**：依這個模組的內容性質挑合適的圖，不是每個模組都用同一種：
   - 資料實體與欄位關聯 → `erDiagram`（欄位標 PK/FK）
   - 跨模組／跨層互動順序 → `sequenceDiagram`
   - 處理邏輯或決策流程 → `flowchart`
   - 部署或資源拓撲 → `block-beta`
   圖後接一段「讀這張圖時，先看什麼、再看什麼」，不是重述圖裡畫了什麼。
4. **逐一深入每個對外行為或子功能**：這個行為的來龍去脈 → 一張圖 → 讀圖指引 → 一張表格，欄位依內容性質決定（例如資料欄位用「欄位｜來源｜用途」，對外服務介面用「方法或事件｜位置｜處理內容｜輸出結果」），不套固定表格式。有實際協定或格式的內容（API、設定檔、訊息格式）直接給具體範例，不用抽象詞帶過。
5. **不變式與邊界條件**：任何狀態下必須成立的約束、合法輸入範圍、例外處理策略。
6. **完成條件**：這個模組的 How 交代完後，讀者應該能確認的幾件事，寫成可查核的清單，不是「寫完就好」。

模組還沒有這些內容時，呼叫 `/plan` 建立；已有時，`code-build.instructions.md` 的 Implementation SOP 直接讀取使用。
